# 设计笔记与路线图

## 一些取舍

**为什么核心用 NumPy 而不是直接上 PyTorch？**
音视频对齐里真正“难”的部分往往是数据管线、指标定义与同步逻辑，而不是某个
卷积核。把这些用 NumPy 写清楚，既能在 CPU 上快速迭代，也让实现本身成为可读的
参考。神经网络编码器留给可选的 torch 后端。

**为什么损失同时给出 InfoNCE / CLIP / NT-Xent？**
它们对应不同的负样本假设：InfoNCE 单向、CLIP 双向对称、NT-Xent 把两模态当作
两个视图。把三者放在一起，方便对照它们在同一批数据上的行为。

**同步为什么基于时间包络的互相关？**
音频能量包络与视觉运动能量包络在事件发生时会同时“跳变”。归一化互相关是一个
无需训练、可解释、对幅度不敏感的偏移估计基线，很适合作为更复杂模型的对照。

## 已知局限

- 视觉特征目前是手工特征（颜色 / 运动 / 网格池化），不是学习到的表示。
- 检索索引是暴力打分，面向正确性与可读性，不追求大规模吞吐。
- 合成数据只覆盖“共享隐变量 + 线性映射”这一类结构。
